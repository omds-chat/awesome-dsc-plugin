# 合集流水线设计：catalog 驱动与 pages 分发

> 本文说明本合集从登记到分发的机制与取舍，写给合集维护者与准备投稿的插件作者。
> 事实以仓库内的 `README.md`、`catalog/README.md`、`.github/pipeline.README.md`、`.github/bundle-layout.README.md` 与脚本为准；本文不重复字段表，只解释为什么这样定、边界在哪里。
> 本文不涉及任何证书材料的生成、签发、续签或替换。

## 一、catalog 驱动模型

### 1.1 来源只有一种：作者自己的站点基址

本合集不托管插件源码，也不从 Release 取产物。作者在 `catalog/` 里登记自己的站点基址，CI 按该基址拉取作者发布的全部版本，再用合集自己的终端签名证书重新签名。

| 来源 | 是否使用 | 说明 |
|:---:|:---:|:---:|
| 作者站点基址 `base_url` | 使用，唯一来源 | 登记在 `catalog/<作者>/<插件>/plugin.json`，版本与产物都从这里取 |
| GitHub Release 资产 | 不使用 | Release 只承载 pages 包，不放插件产物 |
| 镜像与 CDN | 不使用 | 拉取链路只有作者站点，出现分歧时没有第二份可比对的来源 |
| 本仓库内的插件目录 | 不使用 | 仓库里没有 `plugins/`，收录内容不进源码树 |

### 1.2 登记什么、不登记什么

| 对象 | 登记位置 | 内容 | 进 git |
|:---:|:---:|:---:|:---:|
| 作者身份 | `catalog/<作者>/author.json` | 用户名与主页地址 | 是 |
| 作者公钥 | `catalog/<作者>/author_pub.pem` | 作者自持密钥对的公钥，必交 | 是 |
| 插件登记 | `catalog/<作者>/<插件>/plugin.json` | 名称、说明、许可证、源码仓库、站点基址、可选标签 | 是 |
| 插件版本 | 不在本仓库登记 | 由 CI 从站点基址发现 | 否 |
| 插件产物 | 不在本仓库 | 由 CI 拉取后写入构建产物 | 否 |
| 分发包索引与清单 | 不在本仓库 | 全部是构建产物，只在 pages 包里出现 | 否 |

登记与产物分离的两个后果，都是刻意的：

- 作者改动自己的站点不会改动本仓库；本仓库只记录「在哪取」，不记录「取了什么」。
- 仓库里没有空基线，因此仓库级校验只读 `catalog/` 与 `certs/`，不需要任何构建产物。

### 1.3 一次构建的阶段与失败后果

| 阶段 | 输入 | 动作 | 失败后果 |
|:---:|:---:|:---:|:---:|
| 登记校验 | `catalog/` | 字段、公钥格式、标签取值、作者名与插件名规则 | 登记错误，整体中止 |
| 读回 ci-memory | `ci-memory` 分支的 `layer-manifests/` | 按层读回上一版清单，只用于沿用 `revision`；分支里缺该层时过渡回退到已发布站点 | 分支缺失或工作区不是 git 工作区，整体中止，不代为创建 |
| 版本发现 | 作者站点 `versions.json` | 取版本列表与 `latest`，版本号必须是三段语义化版本，`latest` 必须在列表内 | 该插件剔除 |
| 产物拉取 | `<base_url>/<版本>/` | 取 `meta.json`、`plugin.js`（单文件 1 MB 上限）与可选 `plugin.js.author.sig` | 该插件剔除；作者签名取不到或为空只记警告，不影响该插件 |
| 元数据对齐 | 远端 `meta.json` | 名称与登记一致、版本号与目录名一致、产物非空 | 该插件剔除 |
| 产物网络自审 | 每个 `plugin.js` 的文本 | 扫描全局 `fetch(`、`XMLHttpRequest`、`WebSocket`、`EventSource`、`navigator.sendBeacon` 与 `import()` 远程地址 | 该插件剔除 |
| 重新签名 | 每个 `plugin.js` | 用合集终端签名证书生成 `plugin.js.sig` | 构建失败 |
| 清单生成与签名 | 三层目录 | 计算 SHA-512、写 `manifest.json`、每层再生成同名 `.sig` | 构建失败 |
| 组装 | site 产物、`catalog/`、`certs/`、`plugins/` | 拼成 pages 包，生成 `plugins.json`、`catalog/index.json`、`catalog/anomalies.json` | 构建失败 |
| 交叉与自检 | 组装结果 | 索引与插件树一致、证书链与全部签名可验 | 构建失败 |
| 写回 ci-memory | 三层清单 | 把本次清单写回与 `main` 无公共祖先的 `ci-memory` 分支的 `layer-manifests/`，供下次构建沿用 `revision` | 写回失败即中止本次发布，见 2.4 |
| 上报 | `catalog/anomalies.json` | 追加到追踪 Issue | 只警告，不阻塞发布 |

所有产出先落在临时目录，全部校验通过后才整体替换输出目录，因此发布不会留下半成品。三类失败的边界见第四节。

### 1.4 「重新签名」的确切含义

| 项 | 结论 |
|:---:|:---:|
| 覆盖范围 | 只对拉取到的 `plugin.js` 原始字节做 CMS 分离签名，产物为同名 `.sig` |
| 不做的动作 | 不重新打包、不压缩、不改写元数据、不做换行规范化 |
| 签名者 | 合集终端签名证书（EEC），私钥只从 CI secret 注入；证书随 pages 包分发 |
| 作者签名 | 作者的 `plugin.js.author.sig` 原样保留，与合集签名并存，靠文件名区分 |
| 作者产物 | 字节、版本号与远端 `meta.json` 内容都不变 |

- 重新签名证明的是「这份字节由本合集在本次构建中签出」，不证明插件行为安全，也不改变插件来源。收录不等于认证。
- 作者签名不是合集签名的替代品，两者回答不同问题：合集签名回答「合集是否原样收录」，作者签名回答「作者是否签过这一份」。
- 作者签名是可选证据，从不阻断收录：验签失败只在报告与日志里警告。合集在登记侧已经审核过作者与插件，作者层只是附加证据，改变不了收录结论，也就没有理由用它把已审核的内容拦下来。公钥与签名两侧缺一不可，只有一侧缺失时判为「未校验」，不能算作通过。

### 1.5 全量重建、不做版本留存

每次发布按 catalog 全量重建 pages 包并整体替换。

| 项 | 内容 |
|:---:|:---:|
| 放弃 | pages 侧保留历史版本、按版本目录增量发布 |
| 换取 | 分发内容与登记信息始终一一对应；任一次发布都能从登记完整重放，不存在「分发里有、登记里没有」的残留 |
| 代价 | 页面上不能回退取用旧版本；下架即从分发内容消失，没有过渡期 |

### 1.6 产物网络自审的口径

插件不得自建网络通道：网络能力由宿主经 `context.net` 提供，插件可以转发或包装，但不能自己开连接。自建通道绕过宿主的连接策略、超时与可观测性，同一插件在不同宿主上的来源与权限随之无从约束，因此这一条落在收录侧，是门禁而不是运行时防护。

扫描器是 `scripts/lib/plugin-network-scan.mjs`，构建在拉取阶段调用，`collection-verify.mjs` 在 pages 包自检时调用，两处用同一份规则。

| 项 | 结论 |
|:---:|:---:|
| 检测对象 | 版本目录里的 `plugin.js` 文本，单文件上限 1 MiB |
| 命中写法 | 全局 `fetch(`（含 `window`、`globalThis`、`self`、`global` 限定）、`XMLHttpRequest`、`WebSocket`、`EventSource`、`navigator.sendBeacon` 与裸 `sendBeacon(`，以及以 `http://`、`https://`、`//` 开头的 `import(` |
| 不命中 | 方法名前是点号的调用，例如 `context.net.fetch(...)`、`net.fetch(...)`；插件转发或包装宿主网络能力因此不受影响 |
| 问题代码 | `PLUGIN_NETWORK_SELFTALK`，每条带命中的字面量与行、列，同一文件最多逐条列出 20 条 |
| 构建期后果 | 该插件剔除，原因进 `catalog/anomalies.json` 与 Issue，其余插件照常发布 |
| 分发自检后果 | `collection-verify.mjs` 报错误，`verify-bundle.mjs` 以非零退出码结束 |
| 已知误伤 | 不做语法解析：注释、字符串与正则字面量里的同名字样同样命中；先赋别名再调用（`const send = fetch; send(url)`）反而漏过 |
| 误伤处理 | 作者在注释或 PR 说明中解释，或改写为 `context.net` 转发 |

扫描结果不改写产物字节，`plugin.js` 的签名对象因此不受影响。

## 二、三层哈希清单的职责

| 层 | 位置 | 覆盖文件 | 签名 |
|:---:|:---:|:---:|:---:|
| L1 | pages 包根 | `meta.json`、`plugins.json`、`plugins/author_manifest.json`，`tags.json` 存在时一并覆盖 | 根目录 `manifest.json.sig` |
| L2 | `plugins/<作者>/` | `author_pub.pem`、`plugin_manifest.json`，文件存在才覆盖 | 同目录 `manifest.json.sig` |
| L3 | `plugins/<作者>/<插件>/` | `versions.json` 与每个版本的 `meta.json` | 同目录 `manifest.json.sig` |

三层各自回答一个问题：

- L1 回答「这次发布收录了谁、有哪些插件」。
- L2 回答「这位作者登记了哪些插件、公钥是哪一把」。
- L3 回答「这个插件有哪些版本、每个版本的元数据是哪一份」。

每层只描述自己目录里的文件，清单条目只含相对路径与 SHA-512，不含任何跨层指针。

### 2.1 每层自洽，层间不收束

| 项 | 内容 |
|:---:|:---:|
| 选择 | L1 不引用 L2，L2 不引用 L3，任何一层可单独发布、单独校验、单独重签 |
| 放弃 | 「一次校验拿到全树摘要」的便利 |
| 换取 | 按插件增量更新：改一个插件只需该插件 L3 的 `revision` 加一，L2 与 L1 不变，客户端只重拉这一层 |
| 不这样做的后果 | 若收束成一份根清单，任何插件发版都会改动根清单，所有客户端都得重拉整份摘要 |

### 2.2 清单不覆盖产物本体

- L3 不列 `plugin.js` 与 `plugin.js.sig`：产物由每个版本的 `plugin.js.sig` 独立签名，清单只描述元数据。
- 理由：签名的原子单位是「一个版本的产物」，清单的原子单位是「一个目录的元数据」。把产物摘要塞进 L3 会让「发一个版本」变成「改一份清单」，也就退回到按目录整体重签。
- 后果：只验清单不能证明产物完整，客户端必须另取 `plugin.js.sig`；反过来，只验产物也证明不了元数据未被改动。

### 2.3 revision 语义

| 项 | 结论 |
|:---:|:---:|
| 取值范围 | 每层独立的正整数 |
| 变化规则 | 该层文件集合或内容变化时加一，不变时沿用旧值 |
| 上一份值从哪来 | 从本仓库 `ci-memory` 分支的 `layer-manifests/` 按层读回；该分支与 `main` 无公共祖先，不承载登记与源码 |
| 为什么必须入库 | 只有清单本身被持久保存，`revision` 才可能单调递增；上一版取不到时该层退回 1，回滚检测随之失去意义 |
| 边界 | `revision` 仍是变更提示，不是可信计数：首次发布或 `ci-memory` 里读不到该层清单时从 1 开始，写回失败则中止发布而不退回旧值，客户端不得把它当作安全判据 |

回滚检测要求同一层的两份清单可比：新清单的 `revision` 必须大于旧清单，客户端才能判断这一层是「变新了」还是「被换回了旧内容」。若计数会重复或倒退，一次把插件树换回旧内容的操作与一次正常发布在摘要层面无法区分。这是清单必须入库、不能用完即弃的唯一理由；存放位置与读回写回的顺序见 2.4。

读回来源（已实现）：脚本按层从 `ci-memory` 分支的 `layer-manifests/` 读回上一版清单；分支里缺该层时才回退到已发布站点的同名 `manifest.json`（过渡回退），两者都取不到才按首次发布从 1 开始。工作区缺失即分支缺失，构建在拉取插件之前报错中止，不代为创建。

### 2.4 清单入库与 ci-memory 分支

清单入库已定，存放位置、分支名与读回、写回的顺序也已定。分支名定为 `ci-memory`，与组织规范的并行分支命名一致；三项细节的结论见本节末尾。

| 项 | 结论 |
|:---:|:---:|
| 存档对象 | 三层清单 `manifest.json`，按层、按目录原样保存 |
| 写回目标 | 本仓库的 `ci-memory` 分支，与 `main` 无公共祖先 |
| 同类做法 | 与 DeepSeek-Chat-Enhanced 的 `dist-history`、`certs`、`trusted-manifest` 这类并行分支一样，把派生状态放在独立分支，`main` 只留登记与源码 |
| CI 读取 | 已实现：构建开始前从 `ci-memory` 的 `layer-manifests/` 读回上一版清单，只用于沿用 `revision`；分支里读不到该层时过渡回退到已发布站点，写回成功后的下一版不再走回退 |
| CI 写回 | 本次构建与全部校验通过后，把新清单写回该分支；写回失败即中止发布 |
| 读回范围 | 只需要清单本体：`revision` 与 `files` 都在清单里，验签不参与本步骤 |

四条取舍：

| 选择 | 放弃 | 理由 |
|:---:|:---:|:---:|
| 清单入库 | 只从已发布站点读回上一版 | 站点是发布态：不可达、被清空或被回滚时上一版就取不到，`revision` 退回 1，单调性丢失。入库后上一版清单是构建的一个确定输入 |
| 写回 `ci-memory` | 写回 `main` | `main` 只承载登记与源码。产物入库会让每次发布都改动 `main`，PR 差异混入构建噪声，仓库级校验还要处理「有清单、无登记」的歧义 |
| 与 `main` 无公共祖先 | 在同一历史里开普通分支 | 普通分支可以被合并回 `main`，归档内容就有机会进入源码主干；无公共祖先让两侧无法合并，`ci-memory` 只能被 CI 追加 |
| 分支承载状态 | 挂在 Release 资产上 | Release 资产随该次发布存在，读完即弃的存储不适合做「上一版」的载体；分支是可连续追加的单点 |

两条边界：

- 清单入库不改变 1.5 的取舍：`ci-memory` 只保存三层 `manifest.json` 与同名 `manifest.json.sig`，不保存 pages 包本体，页面上仍然取不到旧版本。
- `ci-memory` 不在 `main` 的历史里，因此仓库级校验仍然只读 `catalog/` 与 `certs/`，不必为了喂校验而在 `main` 上留任何清单基线。

三项细节的结论：

| 细节 | 结论 | 理由 |
|:---:|:---:|:---:|
| 分支名 | `ci-memory` | 组织规范的并行分支命名表已把 `ci-memory` 登记为本仓库的分支名，职责就是跨构建延续状态，名下的 `layer-manifests/` 存三层清单 |
| 是否每个合集各自一个分支 | 每仓库一个分支 | 本仓库只承载一个合集，写回与读回都不会跨合集冲突，`layer-manifests/` 下不再按合集分目录 |
| 写回失败时如何处理 | 中止本次发布，CI 报错，不沿用旧 `revision` 继续发布 | 沿用旧值会让该层计数不单调，两个不同内容共用一个 revision；中止则把 `ci-memory` 的可用性变成发布的硬依赖，这是可接受的代价 |

本节结论与 `README.md`、`README.en-US.md` 的 `revision` 条文、`.github/pipeline.README.md` 第五节与 `catalog/README.md` 的同名条文保持一致。

### 2.5 `catalog/` 与 `certs/` 不进任何清单

| 目录 | 性质 | 为什么不进清单 |
|:---:|:---:|:---:|
| `catalog/` | 收录登记 | 登记改动由作者 PR 与仓库级校验保证；纳入清单会让每次登记改动都改动分发完整性摘要 |
| `certs/` | 信任材料 | 用来验签的材料若被它自己要参与验证的清单覆盖，形成自指 |

两者都随 pages 包分发，但都不是分发完整性的一部分：登记信息由仓库级校验保证，信任材料由证书链保证。

## 三、插件与合集证书的位置与命名

### 3.1 插件在 pages 包里的位置

| 对象 | 路径 | 必需 | 签名者 |
|:---:|:---:|:---:|:---:|
| 作者目录 | `plugins/<作者>/` | 是 | 无（目录名即用户名） |
| 作者公钥 | `plugins/<作者>/author_pub.pem` | 是（登记侧必交，构建必定写入） | 由 L2 清单覆盖 |
| 作者插件清单 | `plugins/<作者>/plugin_manifest.json` | 是 | 由 L2 清单覆盖 |
| 版本列表 | `plugins/<作者>/<插件>/versions.json` | 是 | 由 L3 清单覆盖 |
| 版本元数据 | `plugins/<作者>/<插件>/<x.y.z>/meta.json` | 是 | 由 L3 清单覆盖 |
| 产物 | `plugins/<作者>/<插件>/<x.y.z>/plugin.js` | 是 | 由同目录 `plugin.js.sig` 覆盖 |
| 合集签名 | `plugins/<作者>/<插件>/<x.y.z>/plugin.js.sig` | 是 | 合集 EEC |
| 作者签名 | `plugins/<作者>/<插件>/<x.y.z>/plugin.js.author.sig` | 否 | 作者公钥 |
| 作者清单 | `plugins/author_manifest.json` | 是 | 由 L1 清单覆盖 |

### 3.2 合集自身证书的位置

| 材料 | 位置 | 进清单 | 随 pages 分发 |
|:---:|:---:|:---:|:---:|
| 合集终端签名证书 | `certs/awesome-dsc-plugin/awesome-dsc-plugin-eec.crt` | 否 | 是 |
| 与私钥配对的公钥 | `certs/awesome-dsc-plugin/awesome-dsc-plugin-eec-secret.pub` | 否 | 是 |
| 根证书 | 不在本仓库的分发内容内，由 DeepSeek-Chat-Enhanced 的 `certs` 分支分发，网页用内嵌指纹核对 | 否 | 否 |
| 合集签名私钥 | 只从 CI secret 注入，入库即违规 | 不适用 | 否 |
| 根证书私钥 | 只在根证书机构的离线环境持有 | 不适用 | 否 |

两条硬约定：

- pages 包根目录没有 `eec.pem`。合集证书只有一个固定位置，客户端不必猜，也不必按产品演进改路径。
- `certs/` 下只放来源文件夹：文件夹名即来源 id，文件名以 `<来源 id>-` 开头。散落文件、嵌套目录与私钥材料都会被仓库级校验拒绝。

旧布局的根目录 `eec.pem` 只作兼容回退保留，不作为新合集的写法：多个来源共用同一位置的固定文件名会互相覆盖，而「按来源分文件夹」让本合集与内部合集、模板骨架共用同一套定位规则。

### 3.3 命名与层级的理由

| 对象 | 规则 | 理由 |
|:---:|:---:|:---:|
| 作者目录 | 与 `author.json` 的 `username` 逐字符一致，按 GitHub 用户名规则校验且大小写不敏感唯一 | 目录名就是客户端拼路径用的键，两处不一致会让同一作者出现两个目录 |
| 插件目录 | 取插件名去掉 `@scope/` 之后的部分 | 与版本目录里 `meta.json` 的 `name` 可交叉核对，避免作用域前缀造成双层目录 |
| 版本目录 | 三段语义化版本号，与 `meta.json` 的 `version` 一致 | 版本列表要与目录树严格相等，客户端才能按 `latest` 直接拼出产物地址 |
| 签名文件 | 与被签文件同名加 `.sig`；作者签名再加 `.author` | 并列存放、靠文件名区分签名者，不需要额外的签名清单 |
| 证书文件 | `<来源 id>-eec.crt` 与 `<来源 id>-eec-secret.pub` | 文件名自带来源 id，从一个文件就能判断它属于哪个来源 |

## 四、异常插件剔除与上报

### 4.1 三类失败，三种后果

| 类别 | 判定 | 后果 | 理由 |
|:---:|:---:|:---:|:---:|
| 登记不合规 | `catalog/` 里的文件本身不合法：缺字段、名称与目录不符、标签结构或取值不合规、公钥不可解析 | 整体中止，一个插件都不发布 | 这是作者需要修正的登记错误，发布出去只会把错误扩散给客户端 |
| 运行期异常 | 站点拉取失败、远端 `versions.json` 不合法、远端 `meta.json` 与登记不符、产物为空或超限、产物命中网络自审 | 只剔除该插件，其余照常发布 | 外部原因或作者侧产物问题，与本合集和其他作者的登记无关 |
| 构建自身故障 | 签名失败、清单生成失败、分发自检失败 | 整体中止 | 既不是单个插件的问题，也不是作者能修的；发布不完整的分发内容比不发布更糟 |

### 4.2 剔除的语义

| 项 | 结论 |
|:---:|:---:|
| 是否等于下架 | 不等于。剔除是「本次不发布」，登记目录仍留在 `catalog/` |
| 恢复方式 | 作者修好站点后，下一次发布自动回到分发内容，不需要重新提交登记 |
| 在 pages 包里的痕迹 | 不写入 `plugins/` 树，不出现在 `plugins.json` 与 `catalog/index.json`，只出现在 `catalog/anomalies.json` |
| 作者整体剔除 | 该作者名下插件全部剔除时，整个作者目录不写入本次 pages 包，不留空目录 |
| 登记副本 | 被剔除的作者与插件不复制进 pages 包的 `catalog/` 副本，交叉校验因此可以直接比对两棵树 |

### 4.3 上报

| 项 | 约定 |
|:---:|:---:|
| 通道 | 只用 Issue，不写进发布产物的其他位置；工作流需要写 Issue 的权限 |
| 聚合方式 | 标题固定的一条追踪 Issue：已存在就追加评论，不存在就新建 |
| 正文内容 | 本次发布的版本标识、异常条目表格（作者、插件、失败阶段、失败原因）与「已自动剔除、未阻塞发布」的说明 |
| 失败处理 | 令牌缺失、权限不足、接口报错都只警告并正常退出，工作流步骤另有兜底，确保上报问题不阻塞发布 |
| 可离线检查 | 支持只打印请求体、不发真实请求的模式，便于补报前先核对内容 |

### 4.4 取舍

| 项 | 内容 |
|:---:|:---:|
| 选择 | 单个插件的运行期故障不阻塞整次发布 |
| 放弃 | 任一插件异常即整次中止 |
| 理由 | 站点不可达、上游误发都是外部原因；整次中止会把其他作者的登记一起卡住，代价与故障范围不成比例 |
| 代价 | 一次发布可能少收几个插件，用户看到的是「这个插件这次不在」，而不是构建失败 |
| 缓解 | 剔除一定留痕：`catalog/anomalies.json` 随 pages 包分发，Issue 里有条目，交叉校验保证索引与插件树不会各说各话 |
| 边界 | 不是静默跳过。上报失败只影响通知，不改变「已剔除」这一事实 |

## 五、站点与 pages 包的关系

### 5.1 一处设置，两个产物

| 对象 | 位置 | 去向 |
|:---:|:---:|:---:|
| 合集元数据 | `site/meta.json` | 原样复制为 pages 包根的 `meta.json` |
| 预设标签 | `site/tags.json` | 原样复制为 pages 包根的 `tags.json` |
| 站点工程 | `site/` | 构建产物在 `site/dist`，整体复制进 pages 包根目录 |

仓库根不再存放合集设置，也不放任何分发包索引文件：同一份设置只有一个来源，改一处即可。

### 5.2 顶层名字的归属

站点产物只允许贡献 `index.html`、`assets/` 与 `.nojekyll`；下列顶层名字由流水线独占，站点产物占用任何一个都会让构建失败。

| 名字 | 归属 |
|:---:|:---:|
| `plugins/`、`catalog/`、`certs/` | 流水线组装 |
| `meta.json`、`tags.json` | 取自 `site/` 的同名设置 |
| `plugins.json`、`manifest.json`、`manifest.json.sig` | 构建生成 |
| `eec.pem` | 禁止出现，合集证书只在 `certs/<来源 id>/` 下 |

### 5.3 站点只读同源数据，不做密码学

- 页面按固定顺序读同源文件：`catalog/index.json`、`plugins/author_manifest.json`、`plugins.json`、`plugins/<作者>/plugin_manifest.json`、`catalog/<作者>/<插件>/plugin.json`、`plugins/<作者>/<插件>/versions.json`。读到时以它提供的字段为准，读不到才回落到后一步。
- 签名材料只做存在性探测，界面只写「存在」「缺失」「未探测」，并注明未做密码学计算，不代表已验签。
- 理由：站点是展示层。验签需要证书链与 CMS 解析，属于插件市场的职责；若站点也给出「已验签」，两个位置的结论会互相背书，出问题时反而无法定位是哪一层失效。
- `catalog/index.json` 只供站点自己展示，不作为市场省请求的入口：市场不得依赖它加载目录数据，应继续按上表逐层取件。

### 5.4 站点不是分发完整性的一部分

| 项 | 结论 |
|:---:|:---:|
| 站点资产的覆盖 | `index.html` 与 `assets/` 不进任何清单，也不被合集 EEC 签名 |
| 已知边界 | 页面被改不会被清单发现；数据文件被改则会被清单与签名发现 |
| 推论 | 站点不能作为「可信入口」来论证插件可信，判断依据只能是清单与签名 |
| 为什么不纳入清单 | 站点每次构建的字节都会变，纳入清单会让 L1 的 `revision` 每次都加一，「按插件增量」的取舍随之失效 |

## 六、与内部合集在信任模型上的差异

| 维度 | 本合集（社区） | 内部合集（`dsc-inner-plugin`） |
|:---:|:---:|:---:|
| 定位 | 社区投稿的第三方插件合集 | 由组织自研、从产品本体解耦的内部插件索引 |
| 收录来源 | 作者自己发布的站点基址 | 组织内的源码仓库，按来源清单收录 |
| 信任锚 | 根证书机构签发的合集 EEC | 根证书机构签发的网页 EEC |
| 签名对象 | 三层清单与每个版本的 `plugin.js`，逐文件签名 | `dist/` 内的页面文件，整站一份清单与签名 |
| 是否重签产物 | 是，合集用 EEC 为每个产物生成 `plugin.js.sig` | 否，产物签名由作者侧产出，收录只复制 |
| 证书位置 | `certs/<来源 id>/<来源 id>-eec.crt` | 分发根的 `eec.pem` |
| 市场校验顺序 | 证书链、清单签名、逐文件产物签名、作者签名 | 整站清单签名、逐文件签名、作者签名 |
| 版本目录里的签名 | `plugin.js.sig` 必需，作者签名可选 | 作者签名是默认项，没有合集签名 |
| 作者公钥的绑定 | 由 L2 清单覆盖，间接被 EEC 签名绑定 | 由整站签名覆盖 |

### 6.1 差异的根因

| 模型 | 回答的问题 | 为什么这样落签 |
|:---:|:---:|:---:|
| 社区合集 | 合集是否原样收录了这份产物 | 作者是不可信第三方，产物字节必须由合集自己签一遍，客户端才有一个与作者无利益关系的签名者 |
| 内部合集 | 这份页面是否由组织发布 | 作者与发布者是同一主体，整站签名已覆盖索引与产物，再对每个产物复签不会多出一个独立信任主体 |

由此带来的两个直接后果：本合集的签名粒度高、文件多；内部合集的文件少，但「来源可信」依赖整站范围的一致性，单取一个产物无法独立校验。

### 6.2 相同点

| 项 | 结论 |
|:---:|:---:|
| 失败处理 | 都是只警告、不阻断，由用户决定是否继续 |
| 收录语义 | 都是「收录不等于认证」，签名只证明文件与签名者一致，不审查插件行为 |
| 安装通道 | 内部插件同样走市场的普通安装通道，没有快捷通道 |
| 根信任锚 | 都不在各自的分发内容里，由 DeepSeek-Chat-Enhanced 的 `certs` 与 `trusted-manifest` 分支统一分发，网页用内嵌指纹核对 |
| 部署位置 | 都以 pages 包的形式发布静态站点 |

## 七、已否决的方案

### 7.1 结构与分发

| 方案 | 结论 | 否决理由 |
|:---:|:---:|:---:|
| 合集侧增加简介索引以减少市场请求 | 已否决 | 让合集多维护一份派生数据，登记、构建与校验三处都要跟着改，收益不足以抵偿复杂度 |
| 三层收束为一份根清单 | 已否决 | 任一插件发版都会改动根清单，所有客户端都得重拉整份摘要，「按插件增量」的取舍失效 |
| pages 包保留历史版本 | 已否决 | 与「全量重建、直接替换」冲突：保留历史要另立留存与清理规则，分发内容也不再与登记一一对应 |
| 从 Release 取插件产物 | 已否决 | 插件发布权应留在作者手里；Release 只承载 pages 包，避免同一产物有两个可写入口 |
| 根目录放 `eec.pem` | 已否决 | 固定文件名在多来源下会互相覆盖，证书位置也不该随产品演进而换；改为按来源分文件夹 |
| 把 `catalog/` 或 `certs/` 纳入清单 | 已否决 | `certs/` 会形成「用该材料验它自己被覆盖的清单」的自指；`catalog/` 被纳入后每次登记改动都会改动分发摘要 |
| 只从已发布站点读回上一版清单 | 已否决 | 站点不可达或被回滚时 `revision` 退回 1，单调性丢失，回滚检测失效；改为把三层清单写回 `ci-memory` 分支（见 2.4） |
| 把三层清单提交回 `main` | 已否决 | `main` 只承载登记与源码；清单入库到主干会让每次发布都改动 `main`，PR 与仓库级校验都要处理源码与产物的混合 |

关于第一项的边界：pages 包里的 `catalog/index.json` 含插件描述与版本数，形式上接近上述简介索引。它只供本站站点自己展示，不作为市场省请求的入口：市场不得依赖它加载目录数据，按三层清单与 `plugins.json` 逐层取件即可正常工作，站点读不到它也会自动回落到 `plugins/author_manifest.json` 与 `plugins.json`。也不要用聚合索引替代按层取件：聚合索引是构建生成的派生数据，不进任何清单、不参与验签；一旦与三层清单不一致，市场手上没有任何摘要可比，而逐层取件才能同时拿到「这一层有哪些文件」与「摘要是什么」。若把它变成市场取插件元数据的必经入口，就回到了被否决的方案。逐文件的生成者、消费者与签名归属见 [pages-artifacts.md](pages-artifacts.md)。

### 7.2 校验与签名

| 方案 | 结论 | 否决理由 |
|:---:|:---:|:---:|
| 来源自带证书且不校验证书链 | 已否决 | 等于让来源自证：给一份自签证书与自签签名即可通过，正是要消除的问题 |
| 首次信任固定（记录首次见到的指纹） | 未采用 | 首次仍无保证，还要引入状态迁移与失效处理 |
| 用户手动固定来源公钥指纹 | 未采用 | 增加用户负担，与「只警告不阻断」的轻量定位不符 |
| 为 `meta.json` 单独签名 | 已取消 | `meta.json` 已由 L3 清单覆盖并被 EEC 绑定，再签一份不带来额外信任 |
| 为下级合集签发证书 | 已否决 | 信任拓扑只需要「根证书机构到各合集 EEC」一层；多级派生让撤销与责任归属变复杂 |
| 作者签名同时支持两种密钥格式并存 | 搁置 | 需要在浏览器里解析另一种签名格式，收益抵不上实现与验证成本 |
| 浏览器端手写密码学 | 已否决 | 手写实现是长期风险，改用成熟库 |

## 八、未定稿

以下四项机制尚未定稿。8.1 至 8.4 每条写明现行处理方式、候选方向与已排除的选项；本文不对未定项给出结论。清单归档分支的三项细节已定，结论见 2.4。

### 8.1 作者密钥算法

| 项 | 内容 |
|:---:|:---:|
| 现行 | 登记与校验按 Ed25519 裸公钥分离签名执行 |
| 未定 | 作者侧是否统一改为 ECDSA P-256 |
| 冲突点 | 合集签名侧已确认 Ed25519 无法完成 CMS 签名；作者签名若要与之共用一套工具链，算法需要一致，而产品侧的现行校验按 Ed25519 |
| 已排除 | 两种格式并存（搁置，理由见 7.2）；手写实现 |
| 影响面 | 改算法要重建已发布的作者公钥与签名，客户端需同时处理两种公钥 |

### 8.2 作者公钥的锚定强度

| 项 | 内容 |
|:---:|:---:|
| 现行 | 作者公钥由作者提供并登记，进入 pages 后由 L2 清单覆盖，L2 清单由合集 EEC 签名 |
| 未定 | 是否需要为「这把公钥属于该作者」再补一层证明 |
| 候选 | 由合集 EEC 为作者公钥单独签一份；把作者公钥纳入整站范围的签名 |
| 已排除 | 让作者公钥也由根证书机构签发：超出合集职责，且会把作者拉进证书管理 |
| 边界 | 现行做法只保证「合集原样转载了这把公钥」，不保证作者的现实身份 |

### 8.3 多签命名是否在本合集启用

| 项 | 内容 |
|:---:|:---:|
| 现行 | 只认 `author_pub.pem` 与 `plugin.js.author.sig`，其它 `*.author.sig` 不参与校验 |
| 未定 | 是否引入按序号配对的规则，让同一作者可有多个签名者 |
| 参照 | 内部合集已按序号配对支持多签 |
| 已排除 | 在文件名里写签名者姓名：没有组织级注册表，还会与目录名的大小写、转义纠缠 |

### 8.4 合集侧的吊销检查

| 项 | 内容 |
|:---:|:---:|
| 现行 | 构建与分发自检不引入吊销列表 |
| 未定 | 是否在构建期强制吊销检查；以及证书被吊销时应判为「剔除该插件」还是「整次构建失败」 |
| 已排除 | 在合集仓库内自建吊销列表分发：吊销状态只能有一个发布方，多份列表会互相矛盾 |
